# RakForest

**ต้นแบบระบบวิเคราะห์เสียงเพื่อช่วยเฝ้าระวังเหตุการณ์ในพื้นที่ป่า**

RakForest เป็นโปรเจกต์ proof of concept ที่ประกอบด้วย pipeline สำหรับเตรียมและฝึกโมเดลเสียง, local API สำหรับ inference และเว็บต้นแบบสำหรับอัปโหลดเสียง ตรวจผล และประสานงานเจ้าหน้าที่ โมเดลปัจจุบันรับไฟล์เสียงที่ผู้ใช้ส่ง ไม่ได้เชื่อมต่อไมโครโฟนหรืออุปกรณ์ IoT ภาคสนาม

## ภาพรวมโครงการ

พื้นที่ป่ามีขนาดใหญ่และเข้าถึงยาก การลาดตระเวนอย่างเดียวอาจทำให้การรับรู้เหตุผิดปกติล่าช้า โครงการ RakForest จึงมุ่งทำต้นแบบที่นำเสียงจากจุดเฝ้าระวังมาเป็นข้อมูลช่วยคัดกรองเหตุการณ์ เช่น เสียงไฟป่า เลื่อยยนต์ ยานพาหนะ กิจกรรมมนุษย์ สภาพอากาศ และเสียงธรรมชาติ จากนั้นให้เจ้าหน้าที่ตรวจสอบและประสานงานภาคสนาม

ระบบแบ่งการทำงานเป็นสองส่วนที่เชื่อมกัน:

1. **ส่วน Machine Learning** เตรียมชุดข้อมูลเสียง ฝึกและประเมินโมเดล CNN แล้วให้บริการวิเคราะห์เสียงผ่าน API
2. **ส่วนปฏิบัติงาน** ให้หน่วยงานหลังบ้าน/ส่วนกลางรับไฟล์เสียงและตรวจผล ก่อนมอบหมายเหตุให้เจ้าหน้าที่ภาคสนามตรวจสอบและส่งผลกลับ

```text
เตรียมข้อมูล → ฝึก/ประเมิน log-Mel + CNN → บริการวิเคราะห์เสียง
                                            ↑
ไฟล์เสียงจากจุดเฝ้าระวัง → หน่วยงานส่วนกลางตรวจผล/มอบหมายงาน
                                            ↓
                               เจ้าหน้าที่ภาคสนามตรวจพื้นที่
                                            ↓
                             รายงานผล → ส่วนกลางปิดงาน
```

### บทบาทของหน่วยงานและผู้ใช้งาน

| ผู้ใช้งาน | หน้าที่ในกระบวนการ |
| --- | --- |
| **หน่วยงานหลังบ้าน / ส่วนกลาง** | ดูภาพรวมเหตุการณ์และตำแหน่งเสาเฝ้าระวัง จัดการข้อมูลเสา อัปโหลดไฟล์เสียงพร้อมเลือกเสา ติดตามผลวิเคราะห์ ตรวจสอบคะแนนและหลักฐาน ตัดสินใจว่าจะส่งเจ้าหน้าที่ภาคสนามหรือไม่ มอบหมายงานพร้อมบันทึกหมายเหตุ ติดตามผล และปิดงานพร้อมเหตุผล |
| **เจ้าหน้าที่ภาคสนาม** | ดูรายการงานที่ได้รับ มองตำแหน่งและรายละเอียดเหตุ รับทราบงาน ลงพื้นที่ตรวจสอบ แล้วส่งผลว่า **พบเหตุ**, **ไม่พบเหตุ** หรือ **ไม่สามารถตรวจสอบได้** พร้อมบันทึกหมายเหตุและแนบภาพประกอบ |

### ลำดับการทำงานของเหตุการณ์

1. เจ้าหน้าที่ส่วนกลางเลือกเสาเฝ้าระวังและอัปโหลดไฟล์เสียง ระบบเก็บไฟล์และข้อมูลตำแหน่งของเสาไว้กับงาน
2. เว็บส่งไฟล์ไปยังตัววิเคราะห์เสียง ซึ่งอาจเป็นผลจำลองหรือ local inference API
3. เมื่อวิเคราะห์สำเร็จ ระบบสร้างเหตุการณ์สถานะ **รอตรวจสอบ** พร้อมคะแนนแยกตามประเภทเสียงและข้อมูลช่วงเสียง (หาก API ส่งมา)
4. เจ้าหน้าที่ส่วนกลางฟัง/ตรวจผล แล้วเลือกส่งงานให้ภาคสนามพร้อมหมายเหตุ หรือปิดรายการที่ไม่ต้องส่งต่อโดยระบุเหตุผล
5. ภาคสนามรับทราบงาน ตรวจสอบพื้นที่ และส่งผลการตรวจพร้อมหมายเหตุหรือภาพ
6. ส่วนกลางตรวจรายงานและปิดงาน

สถานะงานในเว็บเรียงตามกระบวนการเป็น `pending` (รอตรวจสอบ) → `dispatched` (ส่งงานแล้ว) → `acknowledged` (ภาคสนามรับทราบ) → `submitted` (ส่งผลตรวจแล้ว) → `closed` (ปิดงาน) การแจ้ง Telegram ในต้นแบบเป็นเพียงการจำลองแยกจากสถานะงาน ไม่ได้ส่งข้อความจริง

**ขอบเขตปัจจุบัน:** เว็บมีบทบาทส่วนกลางและภาคสนามสำหรับสาธิต ยังไม่มีพอร์ทัลประชาชนหรือระบบผู้ใช้จริง การอัปโหลดเป็นการส่งไฟล์โดยผู้ใช้ ไม่ได้รับเสียงอัตโนมัติจากไมโครโฟน/IoT และข้อมูลเว็บเก็บในเบราว์เซอร์ ไม่ได้แชร์ข้ามหน่วยงานหรือผู้ใช้

## องค์ประกอบของโครงการ

- **ข้อมูลและ Machine Learning:** โน้ตบุ๊ก Python สำหรับดาวน์โหลดข้อมูล ทำ EDA/cleaning สร้าง manifest ฝึกและประเมินโมเดล ทดลอง inference และตรวจทานเสียง
- **บริการวิเคราะห์:** FastAPI โหลด checkpoint และทำ preprocessing/inference ให้ตรงกับโมเดล
- **เว็บปฏิบัติงาน:** Next.js แสดง dashboard แผนที่ เสา งานอัปโหลด เหตุการณ์ และการติดตามผลภาคสนาม
- **ที่จัดเก็บต้นแบบ:** IndexedDB ใน browser เก็บข้อมูลเสา เหตุการณ์ งาน และไฟล์แนบ โดยยังไม่มีฐานข้อมูลส่วนกลาง

## โมเดลเสียง

โน้ตบุ๊กฝึกปัจจุบันใช้ **log-Mel spectrogram ร่วมกับ CNN** โดยแปลงเสียง mono ที่ 16 kHz เป็นช่วงละ 4 วินาที ใช้ 64 mel bands, `n_fft=1024`, `hop_length=320` และปรับมาตรฐาน log-Mel ของแต่ละช่วงก่อนป้อนโมเดล

เป็นการจำแนกแบบ **multi-label**: เสียงหนึ่งช่วงมีได้หลายคลาส โมเดลใช้ sigmoid แยกคะแนนแต่ละคลาส และฝึกด้วย `BCEWithLogitsLoss` ไม่ใช่ softmax แบบเลือกได้เพียงคลาสเดียว คลาสใน config ปัจจุบันมี `fire`, `chainsaw`, `vehicle`, `human_activity`, `threat_tactical`, `weather`, `natural_ambient`, `silence` และ `other` การผสม waveform ระหว่างตัวอย่างใน train split ใช้เป็น augmentation ระหว่างฝึกเท่านั้น

คะแนนและ threshold 0.5 เป็นค่าเริ่มต้นสำหรับทดลอง ไม่ใช่ความน่าจะเป็นของเหตุการณ์หรือเกณฑ์แจ้งเตือนที่ผ่านการ calibrate การรวมผลของไฟล์ยาวใช้คะแนนสูงสุดรายคลาสจากแต่ละช่วงเสียง จึงสื่อว่าโมเดลพบคลาสนั้นในช่วงใดช่วงหนึ่ง ไม่ใช่ระดับความเสี่ยงของพื้นที่

> **สถานะน้ำหนักโมเดล:** ไฟล์ checkpoint ขนาดใหญ่ไม่ถูกเก็บใน Git และไม่มีไฟล์น้ำหนักโมเดลในชุดไฟล์ที่ติดตามของ repository นี้ ต้องเตรียมข้อมูลและรันโน้ตบุ๊กฝึกก่อน จึงจะเปิด API ด้วย checkpoint ได้ นอกจากนี้ outputs ที่บันทึกในโน้ตบุ๊กฝึก/ประเมินบางส่วนเป็นผลจากโค้ด single-label รุ่นเก่า ต้องรันโน้ตบุ๊กใหม่ตามลำดับก่อนนำผลหรือ metric ไปอ้างอิง

## Workflow ของ Machine Learning

รันโน้ตบุ๊กตามลำดับจากโฟลเดอร์รากของโปรเจกต์:

| ไฟล์ | หน้าที่ |
| --- | --- |
| [01_download_datasets.ipynb](notebooks/01_download_datasets.ipynb) | ดาวน์โหลดชุดข้อมูลเสียงจากแหล่งที่กำหนดไว้ ต้องเตรียม credentials ตามที่โน้ตบุ๊กใช้ |
| [02_eda_cleaning.ipynb](notebooks/02_eda_cleaning.ipynb) | สำรวจข้อมูล ตรวจ/ทำความสะอาดเสียงและป้ายกำกับ แบ่ง train/validation/test ตาม recording group และสร้าง manifest |
| [03_train_model.ipynb](notebooks/03_train_model.ipynb) | ฝึก CNN แบบ multi-label จาก log-Mel และเลือก checkpoint ด้วย validation macro-F1 |
| [04_evaluate_model.ipynb](notebooks/04_evaluate_model.ipynb) | ประเมิน checkpoint บน test split ที่กันไว้ โดยไม่ใช้ test เลือกรุ่น |
| [05_infer_new_audio.ipynb](notebooks/05_infer_new_audio.ipynb) | ทดลอง inference กับไฟล์เสียงใหม่โดยใช้ preprocessing ตามโมเดล |
| [06_review_suspicious_audio.ipynb](notebooks/06_review_suspicious_audio.ipynb) | ฟังและตรวจทานคลิปจาก `zenodo_fire` ก่อนพิจารณานำข้อมูลเข้าชุดฝึก |

รายการและตำแหน่งชุดข้อมูลอ้างอิงอยู่ใน [configs/dataset_paths.json](configs/dataset_paths.json) และโค้ดดาวน์โหลดในโน้ตบุ๊ก 01 ข้อมูลดิบ, manifest, ไฟล์ที่สร้างระหว่างฝึก และ checkpoint เป็นข้อมูลเฉพาะเครื่อง/ไฟล์ขนาดใหญ่ จึงไม่รวมอยู่ใน Git ตาม `.gitignore` สถานะที่บันทึกไว้ใน config เป็น snapshot และควรตรวจสอบกับไฟล์ที่มีจริงในเครื่องก่อนรัน

`zenodo_fire` ถูกกันออกจากชุดฝึกของ checkpoint ที่ API รองรับ จนกว่าจะผ่านการตรวจทานป้ายกำกับตาม workflow ในโน้ตบุ๊ก 06

## Web App และ API

เว็บอยู่ใน [rakforest-web-main/](rakforest-web-main/) ใช้ Next.js, React, TypeScript และ MapLibre มีหน้าสำหรับอัปโหลดเสียง ดู dashboard/แผนที่และเหตุการณ์ จัดการเสาสาธิต ส่งงานให้เจ้าหน้าที่ภาคสนาม และบันทึกผลตรวจพร้อมภาพประกอบ

ค่าเริ่มต้น `ML_PROVIDER=mock` ใช้ผลจำลองตามเสา ไม่ได้วิเคราะห์เนื้อหาเสียงจริง เว็บเชื่อมบริการวิเคราะห์ผ่าน HTTP ได้เมื่อกำหนด `ML_PROVIDER=http` และ URL ของ API ตาม [คู่มือ ML integration](rakforest-web-main/docs/ml-integration.md) API อยู่ใน [api_service/](api_service/) และมี endpoint `GET /health` กับ `POST /analyze`

ข้อมูลเว็บและไฟล์แนบเก็บใน IndexedDB ของเบราว์เซอร์เครื่องนั้น ปัจจุบันยังไม่มีฐานข้อมูลกลาง, ระบบยืนยันตัวตนและสิทธิ์จริง หรือการส่ง Telegram จริง ข้อมูลและขั้นตอนในเว็บจึงเหมาะกับการสาธิตและทดสอบในเครื่อง ไม่ใช่ระบบปฏิบัติงานจริง

### เริ่มเว็บโหมดจำลอง

ต้องใช้ Node.js 24.x และ pnpm 11.25.0 จาก PowerShell ที่โฟลเดอร์ราก:

```powershell
Set-Location rakforest-web-main
npm install -g pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm dev
```

เปิด [http://127.0.0.1:3000/login](http://127.0.0.1:3000/login) โหมด mock ไม่ต้องใช้โมเดลหรือไฟล์ `.env.local` รายละเอียดการทดลองใช้อยู่ใน [README ของเว็บ](rakforest-web-main/README.md)

### เชื่อม local inference API

ต้องมี checkpoint ที่ได้จากโน้ตบุ๊ก 03 อยู่ที่ `models/rakforest_audio_cnn_multilabel_best.pt` ก่อน จาก PowerShell อีกหน้าต่างที่โฟลเดอร์ราก ให้ติดตั้ง dependencies และรัน API:

```powershell
python -m pip install -r api_service/requirements.txt
python -m uvicorn api_service.main:app --host 127.0.0.1 --port 8000
```

จากนั้นสร้าง `rakforest-web-main/.env.local` โดยคัดลอก `.env.example` ของเว็บ แล้วกำหนด:

```dotenv
ML_PROVIDER=http
AI_CLASSIFICATION_ENDPOINT=http://127.0.0.1:8000/analyze
AI_CLASSIFICATION_API_KEY=
ML_TIMEOUT_MS=60000
```

เริ่มเว็บใหม่หลังเปลี่ยนค่า env และตรวจ API ที่ [http://127.0.0.1:8000/health](http://127.0.0.1:8000/health) API จำกัดไฟล์เสียงไว้ที่ 20 MiB; การประมวลผลเสียงยาวแบ่งเป็นช่วงละ 4 วินาที API นี้ตั้งใจให้ใช้ในเครื่องและ bind ที่ loopback ไม่ควรเปิดออกสู่อินเทอร์เน็ต

## ข้อจำกัดและแนวทางต่อยอด

- ยังไม่มีการรับเสียงแบบ real-time จากไมโครโฟนหรือ IoT ภาคสนาม
- ประสิทธิภาพกับเสียงที่มีหลายเหตุการณ์ซ้อนกันจริงยังต้องยืนยันด้วยข้อมูลที่ตรวจป้ายกำกับแล้ว
- ต้องรัน pipeline ปัจจุบันใหม่เพื่อให้ checkpoint และผลประเมินตรงกับโค้ด multi-label ล่าสุด
- การจัดเก็บข้อมูลข้ามผู้ใช้, authentication, Telegram จริง และ dashboard ภายนอก เช่น Superset ยังไม่ได้เชื่อมใช้งาน
- ข้อมูลจากโมเดลเป็นเครื่องมือช่วยคัดกรอง เจ้าหน้าที่ต้องตรวจสอบก่อนตัดสินใจดำเนินการ
